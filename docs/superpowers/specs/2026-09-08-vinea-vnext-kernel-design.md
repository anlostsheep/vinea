# Vinea vNext：目标驱动与多 Agent 协作内核设计

> 日期：2026-09-08
> 状态：设计定稿；实现计划已编写，尚未执行
> 范围：整体重写内核及其技能契约，不是在旧阶段状态机上继续扩展
> 实现状态：本文件不表示新命令、插件、迁移或端到端能力已经实现
> 实现计划：[Vinea vNext Kernel Implementation Plan](../plans/2026-09-08-vinea-vnext-kernel-implementation-plan.md)

本文记录用户已认可的方向、核心契约与验收边界，是后续实现和审核的依据，不是需要整篇注入每个 Agent 的运行提示词。已有设计文档保留为历史资料；涉及新内核行为的冲突以本文为准，但本文不会自动改变现有运行行为。

## 1. 定位与目标

Vinea 是显式进入、文件优先、本机共享的 AI 开发协作内核。用户决定目标、有效约束、重要取舍和交付要求；Agent 在授权范围内自主选择执行方法；Vinea 保存协作事实、检查状态一致性，并说明交付依据。

新内核不以 brainstorm、plan、implement、check 等阶段的顺序为中心，而以交付约定、工作分工、贡献成果和运行绑定为中心。单 Agent 是只有一个执行者的正常情况，多 Agent 协作不是另一套必经工作流。

产品目标：

- 用户不需要重复解释已确认目标，也不需要维护 Agent 的步骤清单。
- 同一任务可以跨会话、跨宿主接续；职责和有效事实不随执行者变化丢失。
- 在宿主能力与授权允许时，由负责人组织协作、整合贡献并交付。
- 无自动派发能力时，显式接力仍是一等路径，不伪造自动化。
- 保留必要的证据、责任、版本和权限边界，不靠增加审批和提示词长度保证质量。

## 2. 首版范围与非目标

首版支持同一份本地 Git 仓库及其 worktree 之间的共享状态、跨宿主接力，以及隔离工作区内的受控并行实现。

首版不做：

- 活跃任务记录的 Git 跟踪、自动提交、推送或分支间合并。
- 跨机器实时协作、独立 clone 自动共享、自动导出或云端同步。
- Vinea 自有 Hook、daemon、MCP server、常驻调度器或独立应用。
- 固定研究、实现、检查角色组合，以及对所有任务强制独立 reviewer。
- 基于心跳或超时的自动抢占、细粒度业务文件写入强制、自动证据依赖图。
- 自动提交、部署，或将学习推广和归档审批绑定到每次交付。

Vinea 管协作协议，实际的 Agent 启动、消息、等待、停止和工作区隔离由可用且已授权的宿主工具承担。它不是限制同一用户下任意进程访问文件的安全沙箱。

## 3. 显式入口与授权范围

普通编程请求不自动激活 Vinea，也不自动创建任务。用户调用命名入口，或者明确说使用 Vinea，才进入。技能被宿主发现或加载本身不等于用户已经选择进入流程；技能描述和执行逻辑必须尊重这个边界。

进入一个任务后，相关自然语言反馈不需要每轮重新调用技能；无关请求不能自动附着到旧任务。以下是逻辑入口，宿主实际语法与注册方式由适配层实现，不承诺所有宿主具有相同的斜杠语法。

| 逻辑入口 | 本次委托 | 范围边界 |
|---|---|---|
| `/vinea` | 处理完整目标并推进到交付 | 在已明确的任务授权内执行 |
| `/vinea:brainstorm` | 收敛目标、前提和关键取舍 | 不自动实现 |
| `/vinea:plan` | 形成可执行方案 | 不自动实现 |
| `/vinea:continue` | 接续已有目标、职责和授权 | 不自动接管他人职责或扩大权限 |
| `/vinea:check` | 独立核验指定成果 | 默认不改业务代码和外部系统 |
| `/vinea:debug` | 定位、修复并验证问题 | 明确要求只定位时不得修改代码 |
| `/vinea:finish` | 核对并整理交付结果 | 不隐含提交、部署或学习推广授权 |

诊断入口可以保留，但不是日常必经步骤。Brainstorm 和 plan 可以独立使用，不要求先建立完整执行任务。用户随后明确要求开始实现时，可沿用已确认结论，不重新进行阶段审批。

入口限定本次委托范围。对只规划任务说“方案可以”，不能自行解释为实施授权；完整执行中的普通自检也不自动变成新的只读委托。解释后续意图必须结合已有授权和用户明确的新限制，不能仅按单个关键词切换模式。

Vinea 场景下的默认只读核验指不改业务代码和外部系统；已有任务内的必要核验记录仍受任务授权约束。用户明确要求不写任何文件时，只返回结果，不因记录证据而擅自落盘。验证命令自身的副作用也必须处于授权范围内。

## 4. 目标驱动的协作方式

用户体验是理解目标与反馈、收敛实质分歧、形成交付约定、自主执行和验证、交付。这不是新的固定阶段链。

交付约定至少表达目标、范围、有效约束、验收标准及授权边界。已明确的执行请求表达执行意图，不额外询问是否创建任务、是否进入某阶段或是否开始执行。

需要用户决策的情况包括目标冲突、无法同时满足的关键约束、未授权的不可逆或高影响操作，以及超出已约定费用、时间或权限的行动。授权范围内的工具选择、可逆实现细节和普通测试失败由 Agent 自主处理。

TDD、冻结接口、禁止提交等明确约束不能被静默降低。TDD 和委派不是每次开始任务都要展示的选择菜单；未被指定的方法可以由 Agent 在授权范围内选择。

### 4.1 Brainstorm 的收敛原则

借鉴 grill-me/grilling 的决策组织方法，而不照搬无限访谈或固定提问仪式：

- 能通过代码、资料和环境调查回答的事实，由 Agent 自行调查。
- 先形成对目标和分歧的判断，每个问题必须改变一个实质决策。
- 同轮询问前提已经明确、彼此独立的问题；依赖问题在获得反馈后重新组织。
- 反馈用于修正对目标、约束和方案的理解，不是继续朗读预制问卷。
- 授权范围内的可逆实验可用于解决技术未知，不必全部靠用户回答。
- 不再存在必须由用户决定且会改变交付方向的未决问题时停止探索。

不逐节审批，不要求遍历所有分支，不以问题数量衡量讨论质量。

### 4.2 执行与 Debug 的停止判断

没有新增信息或进展、触及已约定预算、权限不足或方向变化时，需要重新评估路径。只有实际需要用户决策时才打断用户，不设置“失败两三次必须询问”的固定次数门禁。

## 5. 核心事实及其所有权

下面是概念职责，不要求对应四张表、四份必填文档或四套独立状态机。

| 概念 | 最少必要事实 | 写入与确认责任 |
|---|---|---|
| 交付约定 | 目标、范围、约束、验收、授权及版本 | 依据用户决定建立或修改，负责人维护记录 |
| 工作分工 | 独立成果、必要依赖、执行实例、工作目录、写入职责与交付对象 | 在任务授权内由负责人组织，执行实例认领并提交成果 |
| 贡献成果 | 产物、快照、证据、遗留问题、目标版本及整合情况 | 贡献者提交，交付负责人核对整合 |
| 运行绑定 | Vinea 执行实例、宿主、可选真实会话 ID、工作目录及工作关联 | 适配层和 CLI 维护，用于恢复上下文而非产生授权 |

授权、分工和宿主能力互不替代。下级分工不能放宽上层约定；负责人也不能自行修改用户给出的关键约束。明确的用户反馈可以构成变更决定，不必为同一决定重复确认；变更记录仍应保留来源并产生新版本。

任务始终有一个可转交的集成与交付负责人，不绑定某个模型、宿主或永久会话。负责人和业务写入者分别表达；负责人变更不自动夺走其他参与者的分工。

分工是可选且稀疏的：仅对需要独立交接、并行执行或单独验收的成果建立分工，不把每个工具调用、调查步骤或临时假设做成子任务。单 Agent 不需要模拟一套多人组织。

## 6. 契约一：本机唯一事实源

### 6.1 位置和共享边界

权威状态位于 `<Git共同目录>/vinea/`。CLI 根据 Git 返回的共同目录定位，不直接拼接当前工作目录下的 `.git`，也不硬编码主工作树的绝对路径。

同一仓库的主工作目录与 linked worktree 共用此权威源。不同机器或独立 clone 不共享，即使远端相同。状态不进入 Git 跟踪，不因普通 commit、push 或切换业务分支而作为任务文件参与版本流转。

建议的职责布局如下；具体文件名和序列化格式属于实现设计，不改变单一权威源原则：

```text
<Git共同目录>/vinea/
    tasks/       # 交付约定、分工、持久职责占用、贡献和交付记录
    snapshots/   # 必要快照内容、清单和关联信息
    runtime/     # 可重建会话绑定、短期锁和诊断信息
```

任务事实不是缓存。重启宿主、替换 Agent 或清理会话绑定不能丢失任务或释放职责。记录执行者占用及代次的事实必须持久保存，不能仅放在可清理的运行绑定中。

### 6.2 失败和兼容边界

- 缺失、损坏或存在歧义的权威源必须明确报告，不在当前 worktree 偷偷创建第二份。
- 初次初始化与已有源失联必须区分；是否创建本地状态依据用户的显式 Vinea 请求和授权判断。
- 旧 `.vinea` 是迁移来源，不是与新目录并行可写的第二个权威源。
- 不静默迁移、删除或改写旧任务；迁移另行制定方案并获得必要授权。
- 不把旧的会话指针当作新内核的写入授权，也不把历史通过记录提升为新版本验收证明。
- 不在非 Git 目录自动执行 `git init`。共享目录中的本地数据仍需要用户自行保护，不承诺跨机器备份。

## 7. 契约二：Continue、职责与交接

Continue 的职责是确定 Agent 为哪个目标工作、承担什么责任、目前哪些事实可信，而不是输出下一项必须调用的技能。

### 7.1 接入语义

| 场景 | 必须行为 |
|---|---|
| 原执行实例恢复且职责仍有效 | 恢复原职责，在原授权内继续，不重新申请同一权限 |
| 原执行者已释放，用户已指定接续 | 完成职责转交后继续，不重复询问已确定的决定 |
| 新 Agent 加入了解或审查 | 不自动取得写入职责或负责人身份 |
| 原职责未释放，新 Agent 要接管 | 明确处理占用和接管，不覆盖绑定后直接开始写入 |
| 无可用宿主会话 ID | 使用明确属于 Vinea 的执行实例标识，不伪造宿主 ID |
| 任务或分工存在歧义 | 展示必要候选并请求选择，不按时间或名称猜测 |

接入上下文只提供必要的共同约定、本人分工、相关增量、事实和证据入口。不灌入完整聊天、全部 journal 或所有参与者的内部推理。Context manifest 是恢复入口，不是阻止相关调查的读取白名单。

### 7.2 写入占用与执行代次

首版对参与协议的 Agent 采用同一工作目录单写。并行实现使用隔离工作区，由负责人整合；不同文件不重叠不等于不需要集成验证。

每次写入职责转交产生递增的执行代次。认领和交接是可检查的原子更新；过期执行者不能以旧代次提交新的有效写入成果或修改职责记录。

| 事件 | 工作 W1 的写入者 | 执行代次 | 结果 |
|---|---|---|---|
| A 正在实现 | A | 7 | A 可以提交本次成果 |
| B 加入查看 | A | 7 | B 不自动取得写入职责 |
| A 释放后 B 接续 | B | 8 | B 开始执行 |
| A 再提交代次 7 的成果 | B | 8 | 拒绝过期协议提交，不能当作当前贡献接受 |

任务级交付责任与具体写入职责分开转移；可以在一次明确交接中组合处理，但不能隐含接管其他仍有效的分工。

这些是 CLI 内部语义，不要求用户依次调用 join、claim、release 等命令。短期锁保护记录一致性，不依赖长期持锁、心跳或自动超时回收来推断 Agent 存活。

### 7.3 正常交接与异常接管

正常交接需要保存已完成成果、未解决问题及必要证据，原执行者结束本次写入职责后由接手者继续。

原执行者状态不明时，不根据沉默、会话断开或删除绑定自动判断其停止。无法确认停写时，不让新 Agent 在原目录直接接管写入；可从已有完整快照进入隔离工作区，保留原目录和未确认改动。缺少可恢复快照或遇到范围冲突时，报告实际缺口，不丢弃或擅自合入旧改动。

执行代次只能拒绝遵循协议的过期操作，不能阻止旧进程直接修改业务文件。物理写入安全由真实的宿主停止能力、工作区隔离及用户决策保障，不将账本记录冒充进程终止证明。

## 8. 契约三：快照、证据与交付

### 8.1 分开记录不同事实

| 事实 | 责任主体 | 含义 |
|---|---|---|
| 贡献已提交 | 贡献者 | 已提供某份成果及验证记录 |
| 贡献已整合 | 交付负责人 | 已核对并纳入本次交付 |
| 验收证据 | 实际核验者 | 在指定输入和环境下观察到某个结果 |
| 交付回执 | 交付负责人 | 固定本次交付内容、验证范围和剩余缺口 |
| 用户已接受 | 用户 | 用户明确认可交付，不由技术完成状态自动推导 |

上述责任可以由同一个 Agent 承担，不强制第二个 Agent。显式独立 check 必须区分核验身份和本次证据，不能把实现者原有的通过记录伪装成独立复核。

贡献者自己的工作区通过，不自动证明最终代码组合通过。负责人应针对实际整合结果进行相关验证，而不是仅累加子任务的完成声明。

### 8.2 快照与指纹

指纹用于比较，快照用于识别或恢复具体成果。仅保存哈希而没有必要内容或可获取基线时，不能声称可以恢复交付。

工具应从实际工作区计算快照标识，覆盖本次成果所需的未提交改动、新增文件及相关输入，并保存必要的改动内容与基线关联。不要求用户为此创建业务 commit。缺少基线或内容时明确报错，不能用当前工作区替代历史快照。

凭据和不必要的敏感数据不能写入快照或报告；环境对结果的影响应通过必要的非敏感信息、适当指纹及明确的适用边界表达。

### 8.3 证据的最低语义

证据至少关联交付约定版本、实际快照范围、命令、工作目录、必要环境信息、当时结果及来源。来源需区分真实工具采集、Agent 转述和人工确认；不能用任意填写的标志伪装工具已经独立执行。

不强制所有测试改由 Vinea 运行，继续使用已授权的项目和宿主工具。若无法获得独立采集依据，诚实记录来源和局限，不能把 Agent 填写的 pass 当成更强的执行证明。

局部文件指纹相同，只证明已快照内容未变，不能推出依赖、构建配置、测试命令或环境变化后测试仍有效。相关输入变化需要复核；无法判断影响时重新验证或缩小结论范围，不自动声明无需重测。

历史证据保留但不自动给当前版本背书。目标变更后，旧证据的沿用必须说明仍覆盖哪些未变要求，不改写旧记录，也不将未覆盖的新要求标为通过。首版不实现自动失效传播图。

### 8.4 Finish 的完成条件

Finish 聚焦四件事：

1. 已确认的交付要求得到满足，或者用户明确接受了列出的缺口。
2. 本次交付内容明确，未整合的贡献不计入交付。
3. 验证针对实际交付结果，证据范围、来源和结论一致。
4. 相关写入责任已处理，不让仍在进行的修改悄悄改变刚宣称交付的结果。

用户接受缺口不是验证通过；应保留原失败或未验证结论及用户决定。未提交是合法交付状态，无关 dirty 文件不能阻塞当前任务。

完成、提交、部署、用户接受和归档分别表达。完整执行与完整 debug 的结束不要求用户再次调用 check、finish 或归档命令。学习推广需用户明确接受，但不扣住已经完成的成果。

交付回执固定指向当时成果。后续修改不能覆盖旧快照、旧证据或旧交付结论。

## 9. Debug 的完整契约

Debug 是执行意图，不是每个任务必须经过的阶段。

| 场景 | 行为 |
|---|---|
| 显式 debug 或明确委托修复 | 在授权内完成排查、修复及相关验证 |
| 明确只定位、不改代码 | 只交付证据、原因判断、建议和不确定性 |
| 完整开发委托中的自测失败 | 自主调试修复，不要求额外调用 debug |
| 独立只读 check 发现缺陷 | 报告问题，不自动升级为业务修改 |
| 修复需要改变目标、公共契约、生产或其他授权边界 | 在具体决策点停下，不借修 bug 扩大范围 |

调试需区分预期与实际、事实与假设、已确认根因与缓解措施。修复应对应问题原因，并验证原问题与相关回归。不能复现或无法充分验证时，明确说明替代依据和剩余不确定性，不声称已经确认根因或验证修复。

不强制每个问题写长诊断、列固定数量的假设或派发多个 Agent。协作按需要组织，复用统一分工和成果契约。

Continue 接续调试时，应提供复现入口、证据、已排除及待验证假设、当前改动、未完成验证和职责权限。下一步是建议，不是固定命令；接手者不能把历史假设当成事实，也不无理由重复已经完成的调查。

交付前的问题纳入当前目标的修复工作；交付或归档后的问题建立关联原交付的新修复任务，继承仍有效的约束和上下文，保留原交付快照及验收历史。新增需求或契约变化需明确识别，不能伪装成对原目标的普通修复。

## 10. 轻量实现约束

- 只持久化会改变恢复、责任或验收判断的事实，不登记每个工具调用或内部思考步骤。
- 必要写入的一致性、失败恢复和幂等重试仍需代码保证，但不为每个概念复制一套大型流程引擎。
- 运行时提示只包含当前任务必要约定、分工和证据入口，不重复注入本文、全量历史或固定角色说明。
- 低人工打断依赖实际宿主能力和持续承担整合职责的负责人；负责人中断时，用户可能需要指定或接续负责人。
- 对外区分 CLI 能检查的元数据规则、Agent 应遵守的协作约定，以及宿主才能提供的隔离或执行能力。
- 不以命令数量、角色数量或对象数量证明价值，使用真实任务结果评估。

## 11. 首版验收场景

以下是待实现后的验收要求，不表示当前版本已经通过。

| ID | 场景 | 通过标准 |
|---|---|---|
| A01 | 普通请求与显式进入 | 普通请求不创建 Vinea 任务；显式进入后不重复询问工作阶段 |
| A02 | Brainstorm 与 plan 的范围 | 只讨论或只规划时不实现；关键决策按依赖收敛，停止条件成立后不继续凑问题 |
| A03 | 本机双 worktree 共享 | 不同工作目录定位同一权威源；不存在各自可写的第二份任务事实 |
| A04 | 原执行实例恢复 | 重启后恢复有效职责；清理会话绑定不释放持久占用 |
| A05 | 新 Agent 加入与正常交接 | 仅加入不夺取写权；明确释放和授权接续后不重复访谈目标 |
| A06 | 过期执行者与异常接管 | 拒绝旧代次协议提交；不能确认停写时不在原目录盲目接管 |
| A07 | 并行贡献与最终整合 | 隔离工作区产生贡献；负责人验收实际整合结果，不用子任务通过声明替代 |
| A08 | 未提交交付与可恢复快照 | 保留未提交改动及必要新增文件；快照有实际内容或有效基线；无关 dirty 不阻塞 |
| A09 | 证据变化与独立 check | 相关输入变化不自动沿用；独立核验身份和证据明确，不伪造第二人复核 |
| A10 | 执行内修复与只读边界 | 自测失败可自主修复；显式只读核验不擅自改业务代码或外部系统 |
| A11 | 跨 Agent Debug 接续 | 继承事实、假设和当前改动；不重复无效调查，不升级权限，不把未确认原因写成根因 |
| A12 | 交付后 Debug | 新修复任务关联旧交付；原快照与验收记录不被覆盖；范围变化有用户决定 |
| A13 | 宿主能力缺失 | 明确说明不支持自动派发或停止；仍可显式接力，不伪造已经执行的协作 |
| A14 | 旧数据与故障恢复 | 不静默迁移、删除旧状态或另建权威源；失败重试不产生重复占用或伪造交付 |

效果评估采用相同任务、模型、环境和预算，对照旧流程、新流程及不使用框架的执行。观察验收成功、越界行为、人工确认次数、重复调查、总 token 和耗时，不以减少交互次数单独判断成功。未做真实对照前，不宣称更省 token 或更高成功率。
